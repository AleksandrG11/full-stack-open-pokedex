# Exercise 11.1 — CI for a six-person Python API team

Consider a six-person team maintaining a Python/FastAPI service shortly before its first public release. I would make the CI pipeline run on every pull request and on pushes to the protected main branch. A fast first job would check formatting and linting with Ruff, followed by static type checks with mypy. A separate job would run unit and integration tests using pytest, including tests against an isolated database service. For a releasable commit, the pipeline should build a Python wheel with `python -m build` and a container image, then smoke-test the image rather than assuming that passing unit tests means the deployed artifact works.

GitHub Actions and Jenkins are not the only options. GitLab CI/CD, CircleCI, Buildkite, and Azure Pipelines can all orchestrate these steps. I would initially choose hosted GitHub Actions for this team because six developers are unlikely to benefit from maintaining a dedicated CI server. Hosted runners reduce setup work, provide reproducible ephemeral environments, and integrate naturally with pull requests. However, I would compare expected build minutes, test-data requirements, runner specifications, and deployment-network restrictions before deciding.

Self-hosted runners might be preferable if integration tests require private network access, specialized hardware, strict data residency, or very long builds that make hosted minutes expensive. They introduce patching, credential management, isolation, and availability responsibilities. In either case, I would pin action versions, give jobs minimal permissions, cache dependencies carefully, keep secrets out of logs, and require successful tests before merging. I would also measure pipeline duration and flaky-test frequency after the first few weeks so the configuration evolves with evidence rather than assumptions.
